# 固件文件与升级协议

`dmimu/firmware.py` 提供达妙固件文件解析、升级限制、封包、Boot 应答解码和可离线验证的升级状态机。代码不会打开串口。串口仍由 Host Service 单一拥有；Service 接线负责操作授权、排队、录制/回放互斥、发送、串口重连和版本回读。

协议依据是 [达妙官方仓库](https://gitee.com/kit-miao/dm-imu) 2026-09-24 的 Windows 上位机，commit `ba758fd6106c2b210713bf1ef05800f1688f73c5`，官方 EXE SHA-256 `db5dae031697286256c1b2e27189a87c56f9b68a99d6d69829fdf0871a5776f2`。以下布局与流程从 NativeAOT 程序封包、解析器和状态机确认。官方 EXE/固件原文件不随项目再分发。

## 文件格式

文件末尾 18 字节为：

| 偏移 | 长度 | 内容 |
|---|---:|---|
| 0 | 2 | `55 AA` |
| 2 | 4 | APP 版本，四个单字节分段，例 `02 00 03 00` |
| 6 | 4 | Boot 版本，四个单字节分段 |
| 10 | 8 | ASCII 发行信息，例 `20260922` |

前面的二进制体按原样传输，排除尾部 18 字节，不需要在上位机解密。分页尺寸为 4096 字节，末页用 `FF` 补齐；最多 255 页。每页序号从 1 开始。文件 SHA-256 用于标识上传内容；格式检查与哈希没有为包提供厂商数字签名认证。

官方公开的 `2.0.3.0` 示例文件长度 106,514 字节、正文 106,496 字节、26 页，Boot 版本为 `0.0.0.0`，发行信息 `20260922`。与设备相同的版本会被升级限制拒绝，不能用“重新刷同一版”代替版本更高的升级验证。

版本按照四段整数依次比较。候选版本必须严格高于当前设备版本，2.x 不能降级到 1.x。当前版本必须来自设备应答。

## 请求布局

| 阶段 | 发送布局 | 总长度 |
|---|---|---:|
| 进入升级 | `AA 06 02 0D` | 4 |
| 公告元数据 | `AA DD` + 文件尾部的 16 字节版本/发行信息 + `0D` | 19 |
| 擦除 | `AA EE` + 页数:u8 + 文件总长度低16位:u16LE + `0D` | 6 |
| 写页 | `AA FF` + 页号:u8 + `00 10` + 正文4096字节 + 页CRC:u16LE + `0D` | 4104 |
| 完成后重启 | `AA 00 00 0D` | 4 |

擦除帧里的长度包含原始文件的尾部 18 字节。该字段采用原始文件长度对 65536 取模。页 CRC 覆盖恰好 4096 字节分页正文，不包括帧头、页号、长度和帧尾。

2.x 页 CRC 使用 CCITT-FALSE：多项式 `0x1021`、初值 `0xFFFF`、无反射、无最终异或。官方旧算法先生成同一 CCITT 表，但逐字节折叠时把寄存器左移 **1 位**。本项目命名为 `native-legacy`，避免将其描述为标准 CCITT；`123456789` 的结果为 `0x5F16`。1.x 升级会话必须从已验证的测量/版本帧取得 CRC 模式后显式传入，不能凭版本猜测旧设备使用哪种算法。

`AA 07 55 0D` 是旧版版本查询。升级重启用 `AA 00 00 0D`。

## 应答与状态机

Boot 应答为 8 字节：

```
55 AA | device_id | command | value0 | value1 | value2 | 0A
```

官方 Boot 应答解析器没有对这些 8 字节帧校验 CRC。进入升级、公告和擦除等待 `command=AA`；每页等待 `command=BB` 且 `value0` 等于正在发送的页号；完成等待 `command=CC`，`value0..2` 是大端的 24 位完成位图。没有从这三个命令推断额外错误码。

状态机顺序：

```
ready → entering → announcing → erasing → writing
      → waiting_completion → [单次 reboot 请求] → waiting_reconnect
      → 设备版本回读吻合 → succeeded
```

普通请求等待 2 秒，擦除与最终完成等待 15 秒，普通请求/页发送最多尝试 5 次。仅匹配目标设备和当前页的 ACK 才推进进度。每个新请求前清空之前的 ACK 队列与解析残留；同一批通用 `AA` 应答不会跨越尚未发送的多个步骤。最后一页 `BB` 与最终 `CC` 可以在同一批数据中解析。取消/超时停止继续发送，不自动补发重启，也不自动恢复之前的升级。

位图只有 24 位。对于最多 24 页，官方主机要求置位数量至少达到页数，没有公开位到页号的映射；本实现遵守该计数规则。大于 24 页的文件，最终位图不能单独证明全部分页。本实现逐页要求正确 `BB` 应答，并在重启后回读 APP 版本，与文件版本完全一致才能报告成功。

`UpgradeSession.start/feed/tick` 返回 `Outbound`，由已授权的串口拥有者发送。最终 `CC` 返回一次 `stage="rebooting"` 的重启包，状态变为 `waiting_reconnect`；该重启不按 ACK 超时重试。`verify_reconnected_version` 完成最终验证。`snapshot()` 区分确认页数、写入结果未知与版本已验证。进度达到 100% 仅指分页应答齐全。

## 验证范围

```sh
python -m unittest tests.test_firmware
```

离线测试涵盖官方格式的合成包、边界、填充、版本限制、CRC、碎片和错误帧重同步、ACK 页号与地址匹配、重复应答、超时/重试、24位位图边界、取消、重连版本不符，以及 fake serial 完整事务。旧 CRC 常量也用独立 C 参考实现交叉核对。测试不包含官方固件正文。

没有向真实 IMU 发送进入 Boot、擦除、分页写入或重启指令，也没有完成真实设备刷写验收。二进制还原和离线事务通过只证明已实现相应软件与协议流程，不能声明实际升级已经成功。

## 网页和 Agent 接口

浏览器前缀 `/api/v1`，Agent 前缀 `/api/agent/v1`；沿用浏览器 CSRF/局域网登录与 Agent Bearer/远程 HTTPS 鉴权。

- `POST /firmware/upload`：原始 `application/octet-stream` 文件体；可选 `X-Firmware-Name` 只作显示标签；上限 `255*4096+18` 字节。解析并检查后存入私有运行数据目录的 `firmware/`，Linux 文件 0600、目录继承私有根目录。返回 `id`、版本、发行标记、分页数、SHA256、`current_version`、`upgrade_allowed` 和阻止原因。
- `GET /firmware` / `GET /firmware/<id>`：列出或重新校验已上传文件。固件不存入仓库，也不公开静态下载路径。
- `firmware.inspect`：参数 `{"id":"<文件ID>"}`，沿用 action/operation 模式。
- `firmware.upgrade`：参数必须恰好包含 `id`、`acknowledged:true`、`expected_version`（状态里的 `device.version.app_text`）和 `expected_identity`（状态里的 `identity`）。执行前读取真实设备当前版本与配置，检查身份和严格版本递增，取得一字节 slave_id；网页升级只开放已确认的 2.x CRC 路径。仅上传和检查文件不会发送 Boot 指令。
- `firmware.cancel`：参数 `{"operation_id":"<升级操作ID>"}`。提交时直接唤醒升级 worker，取消不会排在升级后面；已发出的擦除/分页无法撤回。入口发送前取消返回安全取消；进入升级后取消、断开、应答超时、短写或最终版本不符均保留 `uncertain`，不会自动重放。

`status.firmware_busy` 从升级排队起占用设备，禁止新录制、设备参数/校准、探测、数据源切换及其他升级；离线分析/导出仍可运行。现有 reader 是唯一串口读取者：Boot 原始应答进入有上限的队列，操作 worker 驱动状态机并发送 `Outbound`，不创建第二个串口消费者。完成 CC 后最多发送一次 `AA00000D`；原链路保持或重新枚举时，只向已确认身份的设备读取版本。读取版本完全吻合才标记 `succeeded`；重连限时 30 秒。升级期间停止自动选择其他设备。

`status.firmware` 与升级 operation 的 `progress` 提供阶段、确认页数、重试次数、完成位图、版本验证和写入未知状态。分页进度 100% 不能代替 `version_verified:true`。所有 operation 保持原有幂等键与服务重启后的“结果未知、不得重放”规则。

独立 UI 模块 `static/firmware.js` 暴露 `mountFirmwareTools(container,{api,onOperation,onError})`，返回 `update(status)`、`restore()`；沿用项目认证 api，独立轮询长操作并保留操作 ID，刷新页面后只恢复查询。升级按钮要求勾选写入/重启确认，并同时展示当前版本、目标版本和目标端口。

```sh
python -m unittest tests.test_firmware tests.test_firmware_runtime
```

新增集成测试采用 synthetic USB transport：完整 API 升级、同版本/身份/确认保护、即时及排队取消、录制冲突、短写、分页/入口限次重试、USB 重枚举后限定身份重连、单次重启和目标版本回读、私有上传完整性与鉴权。真实设备刷写仍未执行。

## 独立重启与编译信息

`device.restart` 只接受 `{"acknowledged":true}`。执行前只读当前 APP 版本，捕获目标 USB 身份；发送一次已还原的 `AA00000D`，禁止录制/校准/探测冲突并暂停选择其他设备。仅对同一身份进行重连与只读版本查询，回读的 APP 版本与重启前一致才完成操作。没有 Boot ACK 的重启命令不会重发；发送后的异常、版本不符和重连超时返回 `uncertain`。该读回证明设备重新可查询，不单独证明物理复位，所以保留 `physical_restart_verified:false`。

`device.build-info` 不接受参数，发送新版只读 `0x19` 空负载请求。官方 `1403E2FEC` 构建该命令，`1403E2F30` 调用字符串解码，`1403E2F38` 至 `1403E2F57` 修剪 NUL 与空格。本项目保留实际负载 `raw_hex`；可打印 ASCII 子集输出 `text`，其他编码不猜测，也不把字符串擅自拆为日期/版本字段。保存到 `device.build_info`，未经设备响应不显示编译信息。

状态 `device_busy` 包含重启与固件升级，`firmware_busy` 仅表示固件升级。重启和升级的实际设备操作均未运行，本次仅使用 synthetic transport 验证。

## 拖放固件与浏览器检查

固件区支持拖放单个 `.bin`（大小写均可）；松开后上传并检查元数据，不会自动升级。非法后缀、多个文件、缺失正文或超出分页上限会在上传前拒绝；替换文件与上传失败都清空以前的写入确认。设备事务执行期间不接收替换文件。

`tests/firmware_dragdrop.html` / `tests/firmware_dragdrop.mjs` 是独立浏览器检查页，通过本机静态服务器打开 HTML 即可。该页的 API 完全在内存模拟，禁止任何 action 调用，不连接上位机或设备。实际 Chromium 验证 14 项检查通过，包括拖放、原始二进制 File 上传、确认保护、错误文件、占用、失败和普通文件选择；设备写入调用数为零。
